# Hiyo Soul：让关心有记忆、有判断、有后续

Soul 是你负责的教练人格与行为设计。它定义 Hiyo 怎样理解用户、怎样开口、怎样提出建议，以及怎样在下次对话中继续关心。代码放在 `hiyo/soul/`，便于与现有电话执行模块对接。

## 现在补齐了什么

- **多日趋势判断**：先建立个人基线，再判断同一个信号是否连续多天偏离。按用户当地日期聚合，每天多个读数不能充当多天；不同来源、真实和模拟数据分别处理。
- **具体的训练关怀**：记录最近训练部位，结合臀部、股四头肌等部位的酸痛程度、疲劳和睡眠，提出休息、减量或避开相关负荷的建议。健身目标和已核验的日历空闲时间也进入计划。
- **有原因的对话**：先询问和倾听，再安慰、解释、建议。身体不适来自用户明确报告，指标变化来自有来源的数据，不替用户猜测病因或情绪。
- **持久化记忆**：同意后将偏好、观测、训练和反馈存入本地 SQLite；重启后可继续使用。支持查看、清除和保存新反馈来修正旧情况。
- **后续回访**：酸痛、明显疲劳、身体不适或明确的低落反馈可建立回访事项；多日趋势关怀在联系被执行端预留后建立回访。到期时带着具体问题问候，用户明确确认解决后关闭事项。
- **人格与表达分开**：人格、Voice 话术、SMS 话术、干预频率是独立设置。
- **发送前复核**：提案和联系预留分开；预留时再次核验同意、时间、日历、预算、去重，并用事务处理并发请求。预留失败不触发电话，发送失败不自动重拨。

## 三种人格教练

共同任务是认真关心同一个人的长期健康。人格改变关注顺序、激励方式和互动节奏，不改变事实、数据边界和用户的决定权。

### 1. 温柔陪伴型 · The Steady Companion (`gentle`)

**核心感受：我记得你昨天怎么了，你可以慢慢说。**

- 先让用户讲身体和情绪，再一起选择行动。
- 有明确的疲劳或难受反馈时先接住感受，不急于给出一串解决方案。
- 鼓励方式是降低负担、允许休息，让小进步也有意义。
- 回访关心具体变化，而不是每天重复“还好吗”。
- 避免过度亲昵、机械安慰、让用户依赖 AI，或对状态良好的用户强行表示同情。

下肢训练后、睡眠不足且用户表示疲劳的示例：

> “昨天练完下肢，今天臀部和大腿感觉怎么样？”
>
> 用户说很酸、很累后：“谢谢你告诉我。你昨晚也没怎么睡够，我们今天安排休息，给身体一点恢复的时间，好吗？”

适合喜欢被倾听、容易因训练计划产生压力，或需要温暖支持的用户。

### 2. 清晰行动型 · The Practical Coach (`focused`)

**核心感受：我知道你的目标，也会帮你把今天安排得实际一点。**

- 迅速抓住最相关的问题，询问一个关键信息后给出可执行选择。
- 主动回顾上次约定，但允许用户拒绝、调整和休息。
- 鼓励方式是小承诺和可完成的计划，不靠内疚、羞辱或强迫打卡。
- 时间紧时给一个重点、一项行动，必要时结束通话。
- 发现疲劳时同样会建议休息，不把“坚持”理解为硬撑。

同一情境的示例：

> “快速确认一下：今天臀部和大腿有多酸？”
>
> 用户说明疲劳后：“明白。结合昨晚的睡眠，今天建议休息，把恢复放在前面。下次训练我们再按状态安排，可以吗？”

适合时间紧、偏爱明确建议、希望有人协助落实计划的用户。

### 3. 理性解释型 · The Thoughtful Guide (`analytical`)

**核心感受：我会说明为什么这样建议，也会告诉你哪里还不确定。**

- 分清设备记录、用户自述和暂时判断，解释与个人基线的关系。
- 先核对用户的真实感受，再解释一个最有用的依据。
- 鼓励方式是帮助用户理解自己的训练反应，逐渐形成判断能力。
- 只有数据足够时才谈趋势；缺失或过期时直接说明。
- 避免数字堆砌、假精确、长篇讲课和临床结论。

同一情境的示例：

> “昨天练完下肢后，今天主要是哪些部位酸痛？”
>
> 用户说明疲劳后：“这次建议休息，是因为你说仍然很累，而且睡眠比自己的目标少。我们先减少今天的负担，下一次再看恢复情况，你觉得呢？”

适合想理解建议依据、喜欢观察个人规律的用户。

## 人格不等于话多话少

三种人格都支持以下表达设置，电话和短信可以分别选择：

| 表达风格 | 对话表现 |
|---|---|
| Direct | 一至两句短句，一次一个问题和一个重点 |
| Balanced | 简短回应、必要的理由、一个问题 |
| Natural | 自然接话，留出表达空间，不默认变成长篇聊天 |

例如：温柔人格 + Direct 电话 + Natural 短信，或者理性人格 + Direct 电话，都成立。人格可以更换，已获同意的个人记忆保持连续。

## 一次完整关怀怎样发生

1. 收到新数据或用户反馈，检查来源、时间和可用历史。
2. 用户说不舒服，可以产生关怀提案；有足够个人历史且同一信号连续多日变化，也可以产生关怀提案。
3. 联系前核验同意、暂停状态、当地可联系时段、日历、频次和去重。用户没有开启电话时不能自行升级为电话。
4. 开场说明 AI 身份并确认方便，再问具体的问题。安慰和建议取决于用户的回答。
5. 将需要继续关心的事情记为待回访，例如“臀部和股四头肌酸痛”，默认约 24 小时后再检查。
6. 回访会问同一个问题是否好转；用户明确确认后关闭事项。没人回答不代表问题已经解决，也不会自动重拨。

Low / Medium / High 的每日上限目前分别为：0/1/2 次电话，2/3/5 条短信；两次主动联系默认至少间隔两小时。它们都是原型产品设置，可调整。

## 工程使用

```bash
# 仓库根目录；使用已安装项目依赖的 Python 环境
python -m scripts.demo_soul
python -m pytest tests/test_soul.py tests/test_soul_api.py -q
```

演示全程使用标明的模拟数据，在临时数据库里演示三种人格，以及“多日变化 → 联系预留 → 重启 → 回访 → 关闭事项”。不调用模型服务、不发短信、不拨电话。

本地服务提供：

| 接口 | 用途 |
|---|---|
| `GET /api/soul/personas` | 查看人格定义 |
| `POST /api/soul/evaluate` | 输入上下文，得到趋势、计划、联系提案和模型提示词 |
| `POST /api/soul/feedback` | 保存同意后的反馈，创建或关闭回访 |
| `GET /api/soul/memory` | 查看当前 owner 的个人记忆 |
| `DELETE /api/soul/memory` | 清除个人记忆，保留最小联系频次凭据 |

接口沿用现有 operator token 和 tunnel 限制，只服务配置的 owner。时间由服务端提供。`HIYO_SOUL_DB` 可指定本地数据库路径，`HIYO_SOUL_POLICY` 可指定策略文件；默认策略在 `config/soul_policy.json`，会实际加载和验证。

`SoulEngine.evaluate(context, now)` 返回提案，不直接发送。电话模块可使用 `communication.brief`，结构与现有 `build_assistant()` 兼容。执行端拿到最新的可信偏好和日历后调用 `reserve()`，预留成功才可进入它自己的收件人校验、全局 kill switch、活跃通话和花费限制。Soul 的预留不代替这些限制。

反馈的 `resolves_followup_id` 用于明确关闭回访。同一个反馈 ID 可重试但不能被悄悄改写；修正用新的反馈 ID。修改人格等偏好时发送更新后的 profile，记忆开启时保存最新偏好。

## 当前实现的边界

- 这次补齐的是可测试的教练行为、趋势判断和记忆闭环。真实 WHOOP 云端数据接入、日历授权、无人值守调度，以及实时通话中的反馈工具接线仍属于执行端对接工作；原有 BLE 演示循环没有被替换。
- 提示词可以送入现有 Vapi 通话模型，但没有新增独立模型 API，也没有把固定模板伪装成真实模型对话。产品示例展示希望达到的对话，不是通话录音。
- 默认用至少 7 个历史日建立中位数基线，检查最近连续 3 日；分数下降、睡眠减少、静息心率上升的参数都只是可配置的产品启发式，没有临床验证。历史不足或中间缺天时，不宣称确认了持续异常。
- 数据默认不长期保存。开启记忆后保存本地记录，默认保留 90 天；数据库限制为本机用户读写，目前没有加密，尚不适合部署为多用户健康数据服务。
- 设备接入保持中立，第一阶段是 WHOOP。不同设备的评分不能直接混用；未知的心理状态不会由可穿戴数据推断。
